## 1. 🔴 P0 · 私密推送行全量泄漏：`/life/notices` 的过滤是**空操作**

### 问题代码

`backend/app/routers/life.py`

```python
rows = cpp_bridge.life_dao().page_notices(page, size, category, target_grade)
rows = [r for r in rows if not is_private_audience(r.get("target_grade"))]
return ok(paged(rows, len(rows), page, size))
```

`backend/app/db/cpp_driver/src/dao/life_dao.cpp`

```cpp
"SELECT id, title, content, source, category, publish_time "   // ← 没有 target_grade！
"FROM campus_notice "
"WHERE (? = '' OR category = ?) "
"  AND (? = '' OR target_grade = ? OR target_grade = '') "
"ORDER BY publish_time DESC LIMIT ? OFFSET ?",
```

### 事实（只读探针实测，见 §8 复跑方式）

```
① DAO 实际返回的列 = ['category', 'content', 'id', 'publish_time', 'source', 'title']
   含 target_grade 吗 = False
   r.get('target_grade') = None
   is_private_audience(该值) = False
   → life.py 的列表推导会剔除这一行吗 = 不会（过滤是空操作）

② 对照：过滤函数本身是好的
   is_private_audience(None)                  = False
   is_private_audience('__push:reminder:12:D7') = True   ← 函数没问题
   is_private_audience('2026级')                = False
```

DAO 的 SELECT **没有 `target_grade` 列**，所以 `r.get("target_grade")` **恒为 `None`**，
`is_private_audience(None)` **恒为 `False`** ⇒ **列表推导一行都不会剔除**。

### 影响

B18 每天为待办生成「私密推送行」，标题形如 **「【还有 7 天】截止 …」**。
一旦 B18 真实运行，`GET /life/notices` 会把**所有人的个人待办/截止信息**返回给**任何登录用户**。
这与已修复的 `DATA-01`（二手待审泄漏）同级：**内容泄漏给非授权用户**。

### 为什么"实测零泄漏"是**假绿**（两条都是空断言）

**① `backend/tests/test_notice_push.py:65-68`**

```python
public = client.get("/api/v1/life/notices?page=1&size=100", headers=hdr_a)
...
assert not notice_scheduler.is_private_audience(item.get("target_grade"))
```

`item` 来自 API 响应，而**响应里根本没有 `target_grade`** ⇒ `.get()` 返回 `None`
⇒ `is_private_audience(None) = False` ⇒ `assert not False` ⇒ **恒真通过**。

**② `backend/tests/verify_b16_b18.ps1:192-193`**

```powershell
$leak = @($pub.data.items | Where-Object { $_.target_grade -like "__push:*" })
Check "no private leak in /life/notices" ($leak.Count -eq 0) (...)
```

`$_.target_grade` 不存在 ⇒ `$null -like "__push:*"` = `False` ⇒ `$leak.Count = 0` ⇒ **恒真通过**。

**③ 数据库侧的另一重巧合**：实测当前 `campus_notice` 共 10 行，
**私密行 = 0**（作者已用 `purge-private` 回收干净）⇒ 即使断言写对了，在**零私密行**的数据上也会通过。
两个原因叠加，导致"零泄漏"结论从未被真正验证。

> 📌 **教训（建议写进团队规约）**：**断言必须依赖一个"若缺陷存在就必然为真"的可观测事实**。
> 本例正确写法（任选）：
> - **标题比对**：把私密行的标题作为已知字符串，断言它**不出现**在公共列表里（最强、最直观）；
> - **前后差量**：记录调度前 `/life/notices` 的条数与 id 集合，调度后再取一次，断言**集合不变**；
> - **字段存在性前置断言**：`assert "target_grade" in public.json()["data"]["items"][0]`
>   —— 先保证"我要检查的字段真的在"，否则后续断言无意义。
> 与本仓已有的 `jt_db 字符串化导致断言假通过` 是**同一族问题**：断言依赖的东西不存在。

### 正确的修法（且必须一并解决 §6 的分页口径）

不要在 Python 侧过滤 —— **拿不到列就永远过滤不了**。两个可选方案：

**方案 A（推荐，纯 Python，符合本 PR "无需重编译 C++" 的声明）**：
在 `life.py` 里直接用 `cpp_bridge.query` 写带过滤的 SQL，并同时算对 `total`
（照抄 `services/notice.py::_visible_notices` 的写法与同一个常量）：

```python
from app.services.notice import _PRIVATE_LIKE   # 或 notice_scheduler.PRIVATE_TARGET_PREFIX

where = "WHERE (? = '' OR category = ?) AND (? = '' OR target_grade = ? OR target_grade = '') " \
        "AND target_grade NOT LIKE ? "
params = [category, category, target_grade, target_grade, _PRIVATE_LIKE]
total = cpp_bridge.query(f"SELECT COUNT(*) AS c FROM campus_notice {where}", params)[0]["c"]
rows  = cpp_bridge.query(f"SELECT id, title, content, source, category, publish_time "
                         f"FROM campus_notice {where} ORDER BY publish_time DESC LIMIT ? OFFSET ?",
                         params + [size, (page - 1) * size])
return ok(paged(rows, int(total), page, size))
```

**方案 B**：给 `LifeDAO::page_notices` 加 `exclude_target_prefix` 参数（需重编译 C++，
与本 PR"无需重编译"的声明冲突 → 建议并入下一批 C++ 改动并登记）。

**不论哪种，`is_private_audience` 在 `life.py` 的用法都应删除**（在无该列的数据上它永远无效，
留着只会继续制造"看起来过滤了"的假象）。

## 2. 🔴 P1 · `POST /admin/knowledge/purge`：LIKE 通配符未转义 → 一条调用清空知识库

`backend/app/services/knowledge.py`

```python
rows = cpp_bridge.query(
    "SELECT id FROM knowledge_doc WHERE source_url LIKE ? AND status != 2", [f"{p}%"]
)
```

`p = normalize_source(prefix)` 只做了 `strip` / 反斜杠替换 / 截断，**没有转义 `%` 与 `_`**。
⇒ 传入 `source_prefix = "%"` 时 `LIKE '%%'` **匹配全部文档**；
`"_"` 同理（`LIKE '_%'` 匹配任何非空串）。
`admin.py` 的守卫只有 `if not body.source_prefix.strip(): raise err_param(...)` → `"%"` **能通过**。

⇒ 一次管理端调用即**删除全部 knowledge_doc + knowledge_chunk + 向量**（`purge_vectors=True` 默认），
**无 `dry_run` 强制、无二次确认、无最小长度限制、不可回滚**。
B17 的 CLI 同样提供 `--purge-source-prefix`，误敲 `%` 的代价相同。

**建议**（任选其一，建议全做）：
1. 拒绝含 `%` / `_` / `\` 的前缀（`err_param`），并在 docstring 写明；
2. 要求 `len(prefix) >= N`（如 4），避免 `"a"` 这类过宽前缀；
3. 增加 `confirm: bool = False`，未确认时**只返回 `matched` 与候选 id 列表**（预览），
   确认后才真删；CLI 同步加 `--yes`；
4. `purge_by_source_prefix` 内部用 `ESCAPE '\\'` 或改用 `LOCATE(?, source_url) = 1` 做前缀匹配，
   彻底避开通配符语义。

## 5. 🟡 P2 · PDF 解压上限在 `zlib.decompress()` **之后**才判

`parser/pdf_parser.py`

```python
_MAX_STREAM_BYTES = 64 * 1024 * 1024   # 单个流解压上限（防 zip bomb）   ← 意图是对的
_MAX_STREAMS      = 512
...
if fname in ("FlateDecode", "Fl"):
    out = zlib.decompress(out)          # ← 一次性全解，内存已分配
...
if len(out) > _MAX_STREAM_BYTES:        # ← 到这里才判
```

`zlib.decompress()` 会**先分配完整个解压结果**再返回，所以"解压炸弹"在
`len(out) > _MAX_STREAM_BYTES` 之前就已经吃掉了内存（一份 32MB 的合法 PDF 里，
单个高度可压缩流可膨胀到数 GB）。

**建议**：主路径也改用**流式 + 长度上限**（文件的容错分支 `line 221` 已经在用 `decompressobj()`，
只是没传 `max_length`）：

```python
d = zlib.decompressobj()
out = d.decompress(data, _MAX_STREAM_BYTES)   # 超过即停，不再分配
if d.unconsumed_tail:
    warnings.append("流超过 64MB 上限，已截断")
```

其余护栏（`_MAX_STREAMS = 512`、无 XML/DTD 解析 ⇒ **无 XXE 面**）都做得对，值得肯定。

## 6. 🟡 P2 · 过滤放在分页之后 ⇒ `total` 与页长口径错乱

即使按 §1 拿到 `target_grade`，**在 Python 侧过滤分页结果**仍会引入两个新问题：

1. **`total` 失真**：`paged(rows, len(rows), page, size)` 用的是**本页过滤后条数**（`total=len(rows)`
   是既有问题，已在审计记录），叠加过滤后更离谱；
2. **公共行不可达**：DAO 按 `publish_time DESC` 取窗口，**不会因过滤而"补位"**。
   私密行（B18 每天新增，`XJT_NOTICE_PUSH_MAX_ITEMS=500`）会占据窗口位置，
   被剔除后该页就短了，**而后续的公共行不会被顶上来到这一页**
   —— 量大时 `page=1` 可能几乎为空，公共通知从该接口不可达。

⇒ 所以 §1 的修法**必须把过滤下推到 SQL**（方案 A 的代码同时算了正确的 `total`），
一次把"泄漏 + 计数 + 分页"三件事一起解决。
