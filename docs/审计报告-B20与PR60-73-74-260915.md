## 2 · B20 能导致的所有问题

B20 = 「通知表结构扩展」：`campus_notice` 增加 `deadline` / `materials` / `importance` 三列 + `idx_deadline` 索引。
它的 DDL 是 `db/sql/14_notice_extend.sql`。

### 2.1 🔴 P0-①：顺序陷阱**已经发生**，`/life/notices` 现在就是坏的

`feature/backend` 的 `0f21d9f` 把 DAO 改成**无条件** SELECT 这 3 列：

```cpp
// github/feature/backend:db/cpp_driver/src/dao/life_dao.cpp
"SELECT id, title, content, source, category, publish_time, "
"       deadline, materials, importance "        // ← 硬编码，没有"列是否存在"的判断
"FROM campus_notice "
```

而库里**根本没有**这 3 列。**证据（决定性）**：

```sql
-- 用同款 SQL 直接打库：
SELECT id, title, content, source, category, publish_time,
       deadline, materials, importance
FROM campus_notice ORDER BY publish_time DESC LIMIT 1;

-- 实测输出：
ERROR 1054 (42S22) at line 2: Unknown column 'deadline' in 'field list'
```

**反向对照**（证明问题就出在这 3 列）：去掉它们立刻正常 —— `id=9008 校园二手交易平台使用规范`。

**后果链**：
1. `/life/notices` → 500（不是"少字段"，是**整条接口挂掉**）
2. `notice_feed` / `notices/unread` 走的是 Python 侧 `notice_columns()`（**条件式**，安全）⇒
   **同一张表的两条读取路径行为不一致**：一条挂、两条正常
3. 前端通知页直接白屏

**为什么说"已经发生"**：`feature/backend` 已推到远端。任何人把它合进 `dev`、或按它重编译 `jt_db`，故障立刻上线。

### 2.2 🔴 P0-②：DDL 从未执行，B20 全链路是"空中楼阁"

```
campus_notice 上的 deadline/materials/importance 列数 = 0
idx_deadline 索引数 = 0
```

**证据**
```sql
SELECT COUNT(*) FROM information_schema.columns
WHERE table_schema='xiaojietong' AND table_name='campus_notice'
  AND column_name IN ('deadline','materials','importance');   -- 实测 0
```

**连锁阻塞**（任务单里排在这些之后的所有活儿）：
- B20 自身：`/life/notices`、`/notice-feed`、`/notices/unread` 都拿不到这 3 个字段
- **B18 的"带截止时间的通知"推送源永远不启用**（`_notice_rows` 第一行就是 `if not notice_deadline_supported(): return []`）
- B23（`PUT /user/me` 学号）之外的 B23/B24/B29/B30（抽取结果回填）全部无处可写

### 2.6 🟡 P2-②：`_EXTENDED_COLUMNS` 进程内缓存 —— DDL 跑完≠生效

```python
_EXTENDED_COLUMNS: Optional[set[str]] = None
def notice_extended_columns(refresh: bool = False) -> set[str]:
    if _EXTENDED_COLUMNS is not None and not refresh:
        return _EXTENDED_COLUMNS        # ← 缓存，永不自动失效
```

⇒ DDL 执行后**必须重启后端**，否则：
- 字段继续不返回（"我明明跑了 DDL 啊"）
- `/health/detail` 的 `notice_deadline_supported` 一直是 `false`

`feature/backend` 确实加了这两个 health 字段（可观测性，值得肯定），但**缓存本身仍在**。

### 2.7 🟡 P2-③：`attach_extended_fields` 的删除会造成冲突

| 分支 | `notice.py` 是否有 `attach_extended_fields` |
|---|---|
| `dev` | ✅ 有（`/life/notices` 靠它补查） |
| `feature/backend` | ❌ 已删（改为 DAO 直出） |
| `fix/life-notices-paging-regression`（我的分页修复） | ✅ 有（基于 dev） |

⇒ `feature/backend` 合入 dev 时，与我的分页修复**必然冲突**（同一函数区域）。
**不是谁写错了**，而是两条线的假设不同（"DAO 拿不到新列" vs "DAO 直出"）。

### 2.8 🟡 P2-④：`importance` 的 NULL 与 0 无法区分

DDL 注释写明 `NULL = 未打分`，但代码：

```python
def importance_of(row: dict) -> int:
    try:
        value = int(row.get("importance") or 0)   # None 和 0 都落成 0
    except (TypeError, ValueError):
        return 0
```

⇒ "未打分"与"打了 0 分"合并。若将来 B24 用 0 表示"已评估为不重要"，就会与"没评估过"混淆。

### 2.9 🟡 P2-⑤：私密推送行的 `LIKE` 模式未转义（潜在，牵 P0）

```python
_PRIVATE_LIKE = f"{PRIVATE_TARGET_PREFIX}%"      # = '__push:%'
```

`_` 在 SQL LIKE 里是**单字符通配符**。真实误伤概率≈0（需 `target_grade` 前两字符任意 + 第 3–7 位恰为 `push:`）。

**但我没有改它**：`private_notice_ids()` 一旦因转义写错而取空 ⇒ 私密行会**泄漏**（P0 级）。
为一个理论风险去动 P0 路径不划算。建议与"给 DAO 加 SQL 层过滤"一起做。

### 2.10 🟡 P2-⑥：`idx_deadline` 缺失 + `LIKE` 前导通配 ⇒ 全表扫

`private_notice_ids()` 每次请求都执行 `WHERE target_grade LIKE '__push:%'`（**前导通配，索引不可用**）。
`/life/notices` 每访问一次多一次全表扫。数据量小的时候无感，`campus_notice` 长大后是热点。
