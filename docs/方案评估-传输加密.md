# 方案评估：应用层「加盐哈希编码/解码」传输加密

> 评估对象（用户提案原文）：
> 「在服务器端和客户端分别弄两个**加盐哈希解码器和编码器**，在网络传输过程中，**只传输加密过后的数据包**」
>
> 评估人：成员3 ｜ 日期：2026-09-11 ｜ 结论：**不可行（需修正方案目标与技术路线）**

---

## 一、结论先行

| 维度 | 判定 |
|---|---|
| 作为「替代 HTTPS 的传输加密」 | ❌ **不可行** |
| 作为「敏感字段的额外保护」 | ⚠️ 方向可保留，但**实现位置错了**（不该在传输层，该在存储层） |
| 作为「防篡改 / 防重放」 | ⚠️ 合理需求，但应改用 **HMAC + 时间戳 + nonce**，而非"哈希编解码" |
| 作为「口令存储方案」 | ✅ **这才是加盐哈希的正确用途**（但本项目当前无口令登录） |

**一句话**：方案想解决的「传输安全」问题，**HTTPS 已经解决了并且做得更好**；
而方案里「加盐哈希**解码器**」这个构件在密码学上**不存在** —— 哈希是单向的，无法解码。

---

## 二、方案拆解：哪部分合理，哪部分混淆

### 2.1 概念澄清（这是最关键的一点）

提案中把**两个完全不同**的密码学原语混在了一起：

| | **哈希**（含加盐哈希） | **加密** |
|---|---|---|
| 数学性质 | **单向函数**，不可逆 | **双向**，可用密钥还原 |
| 典型算法 | SHA-256、bcrypt、argon2 | AES、SM4、RSA、SM2 |
| 输出 | 固定长度摘要 | 与明文等长的密文 |
| 能否"解码" | **不能** —— 没有"哈希解码器"这种东西 | 能，用密钥解密 |
| 正确用途 | **校验完整性 / 存口令** | **保护机密性** |

因此提案中的「**加盐哈希解码器**」在技术上是不存在的构件：

- 若真的只对数据做加盐哈希再传输 → 服务端**收到的只是摘要，拿不回原文**，业务无法进行
- 若想做"加密后传输、服务端解密" → 那用的是**加密算法**，不是哈希

> 这不是名词之争：混淆会导致实现出**根本跑不通**的东西，或者写出"自己发明的加密"（密码学上极度危险）。

### 2.2 合理的动机内核

去掉术语混淆后，提案想表达的应该是：

> "不希望数据在网络上以明文形式流动，希望客户端加密、服务端解密。"

这个**动机是正当的**，只是解决路径选错了。

---

## 三、为什么不可行：三个致命问题

### ❌ 问题 1：客户端的密钥必然泄露，等于没有加密

这是**最根本**的问题。如果客户端要能加密，密钥就必须存在于客户端：

```text
小程序包（wxapkg）── 解包工具（现成）── 直接读到硬编码密钥
                                          ↓
                            攻击者拿到密钥，即可解密所有数据包
```

| 对比项 | TLS（HTTPS） | 自研客户端加密 |
|---|---|---|
| 密钥存放 | **不落地**，每次会话临时协商（ECDHE） | 必须硬编码/内置在客户端 |
| 密钥泄露后果 | 单个会话失效（前向保密） | **全部历史与未来通信均可解密** |
| 能否被逆向 | 不能（密钥不存在于客户端） | **能**（小程序反编译成熟） |

> 密码学第一原则：**不要把秘密放在攻击者能拿到的地方**。
> 客户端（尤其是小程序）完全在用户/攻击者控制之下。

### ❌ 问题 2：HTTPS 已经提供了更强的保障，自研是"更弱的重复造轮子"

微信小程序平台**强制要求** `https://`（`wx.request` 不接受 http），因此本项目**生产环境必然运行在 TLS 之上**。

TLS 已经同时提供：

| 安全目标 | TLS 的保障 |
|---|---|
| **机密性**（防窃听） | 对称加密（AES-GCM / ChaCha20-Poly1305） |
| **完整性**（防篡改） | **AEAD** 认证加密，任何改动都会导致解密失败 |
| **身份认证**（防冒充服务器） | 证书链 + CA 体系 |
| **前向保密** | ECDHE 密钥交换，历史流量不因长期密钥泄露而暴露 |
| **防重放** | 序列号 + AEAD |

自研方案**无法提供**其中的身份认证与前向保密，却引入了新的复杂度和故障点。

### ❌ 问题 3：增加了真实风险，却没有对应收益

| 引入的风险 | 说明 |
|---|---|
| **自研密码学** | 未经验证的方案极易出现 IV 重用、填充预言、时序侧信道等漏洞 |
| **调试困难** | 抓包看不到明文，线上问题定位成本剧增 |
| **性能损耗** | 双重加解密，小程序端 CPU/电量受限 |
| **密钥轮换困难** | 客户端密钥更新需发版，小程序审核周期以天计 |
| **兼容性** | 其他端（Web 管理后台、第三方对接）需同步实现，协作成本扩散 |

而**安全收益约为零**（因为 HTTPS 已覆盖）。

## 四、本项目的真实安全短板（对比之下更该做的事）

评估方案时也顺带核对了现状 —— 本项目真正该补的安全项**不是传输加密**，而是：

| 编号 | 问题 | 影响 | 状态 |
|---|---|---|---|
| **SEC-07** | 登出完全无效（no-op），被盗 token 在 2h 内无法作废 | **真实可利用** | 待处理（清单 A 组） |
| **SEC-08** | Refresh token 可无限重复使用、无轮换、无吊销 | **真实可利用** | 待处理（清单 A 组） |
| **SEC-09** | 角色粒度粗：`role>=1` 即管理员，高风险能力（全量重建索引）对所有管理员开放 | 权限过宽 | 待处理（待产品确认） |
| SEC-01~06 | 越权/伪造等 6 项 | —— | ✅ **已修复并实测** |
| SEC-10~14 | 限流/CORS/上传/口令脱敏 | —— | ✅ **已修复并实测** |

> ⚠️ **投入产出比提醒**：把精力投入"自研传输加密"的收益趋近于零，
> 而修复 SEC-07/08 能直接消除两个**真实可利用**的会话安全漏洞。

## 五、什么情况下应用层加密才真正有意义（客观列举）

不是所有"应用层加密"都无意义，以下是**正当场景**（本项目目前都不属于）：

| 场景 | 说明 | 本项目是否适用 |
|---|---|---|
| **端到端加密（E2EE）** | 服务器**不持有**明文（如密码管理器、私密聊天） | ❌ 本项目服务端必须处理业务逻辑 |
| **合规强制要求** | 支付、身份证等有**国家标准规范**（如 PCI-DSS、国密 TLCP） | ⚠️ 若涉及，应**遵循标准**而非自创 |
| **防企业代理解密** | 对抗 TLS 中间人（如企业 SSL 审计） | ❌ 校园场景无此需求 |
| **国密合规** | 政企项目可能要求 SM2/SM3/SM4 | ⚠️ 若学院有要求，走**标准国密方案** |
| **口令存储** | **这正是加盐哈希的正当用途** | ❌ 本项目走微信登录，无本地口令 |

## 六、推荐方案（分层，按优先级）

如果目标是"提升整体安全性"，建议按以下顺序推进：

### 第 1 层 · 传输安全（**已完成，无需改动**）

- ✅ 全站 HTTPS（小程序平台强制）
- ✅ 确保 TLS 1.2+，禁用弱套件（部署时在 Nginx 配置）
- ✅ 开启 HSTS

### 第 2 层 · 会话安全（**建议优先，对应清单 A 组**）

```text
SEC-07 登出失效  →  user.token_version 自增，deps 校验版本号
SEC-08 refresh 轮换 →  刷新时校验账号状态 + 作废旧 refresh
```

这是本项目**当前最该做**的安全改进。

### 第 3 层 · 敏感数据存储（**若涉及才做**）

- 手机号 / 身份证等敏感字段：**数据库加密 + 展示脱敏**（`138****8888`）
- 密钥存服务端 KMS 或环境变量，**绝不入客户端**
- 口令（若未来引入）：**bcrypt / argon2 慢哈希 + 每用户独立盐**

> 这里才是「加盐哈希」的正确位置 —— **服务端存摘要，永不传输可逆密文**。

### 第 4 层 · 防篡改 / 防重放（**按需，若确有攻击面**）

若将来出现"接口被脚本批量刷"或"请求被重放"的实际问题，正确做法是**签名机制**：

$$
\text{signature} = \text{HMAC-SHA256}(\text{secret}_{\text{server}}, \; \text{method} \parallel \text{path} \parallel \text{body-hash} \parallel \text{timestamp} \parallel \text{nonce})
$$

- `secret` **由服务端下发短期凭证派生**（不是硬编码在客户端）
- 服务端校验：签名正确 + 时间戳在窗口内（如 ±5 分钟）+ `nonce` 未使用过
- **注意**：这防的是**重放与篡改**，不是"防窃听"（窃听由 TLS 负责）

## 七、如果确实要落地，最小可行形态

若评估后仍决定引入应用层加密，建议**严格限定范围**，避免全局套娃：

| 决策点 | 建议 |
|---|---|
| 加密位置 | **仅对明确列出的敏感字段**（如身份证号），不做全量报文加密 |
| 算法 | **AES-256-GCM**（AEAD，自带完整性）；**不要自创组合** |
| 密钥来源 | 用户登录后由服务端**下发会话密钥**（随 token 生命周期），**不硬编码** |
| IV/Nonce | **每次加密随机生成**并随密文传输（严禁重用） |
| 传输层 | **仍然走 HTTPS**（应用层加密是叠加，不是替代） |
| 密钥轮换 | 与会话绑定，登出即失效 |
| 可观测性 | 加解密失败要有独立日志与告警，不可静默降级 |

> 即便如此，其收益仍主要是**合规性叙事**而非实际安全增量 —— 因为密钥仍在客户端内存中，
> 有能力的攻击者可通过调试/内存 dump 取得。**这一点必须在方案里如实说明**。

---

## 八、总体建议

| 建议 | 理由 |
|---|---|
| ❌ **不要**实施"客户端/服务端哈希编解码"方案 | 概念不成立（哈希不可逆）+ 密钥必泄露 + 重复造更弱的轮子 |
| ✅ **要**确保生产 HTTPS + TLS 1.2+ + HSTS | 这是唯一必需的传输安全措施 |
| ✅ **优先**修复 SEC-07 / SEC-08 | 消除两个真实可利用的会话漏洞，投入产出比最高 |
| ⚠️ **按需**做敏感字段的**存储加密 + 展示脱敏** | 若业务涉及身份证号等，这才是正确位置 |
| ⚠️ **按需**引入 HMAC 签名 + 时间戳 + nonce | 防篡改/防重放，密钥由服务端会话下发 |
| 📌 若学院有**国密合规**要求 | 走标准国密方案（TLCP/SM2/SM4），不要自研 |
