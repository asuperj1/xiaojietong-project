## 1. P1（阻断）· `detectGlass()` 恒返回 `false`：`getAppBaseInfo()` 没有 `system` 字段

### 问题代码（`miniprogram/utils/glass.js`）

```js
const info =
  typeof wx.getAppBaseInfo === 'function' ? wx.getAppBaseInfo() : wx.getSystemInfoSync()
const system = (info && info.system) || ''
```

### 事实

按微信官方文档，`wx.getAppBaseInfo()` 的返回字段是：

```
SDKVersion / enableDebug / host / language / version / PCKernelVersion /
theme / fontSizeScaleFactor / fontSizeSetting
```

—— **没有 `system`**。`system`（形如 `"iOS 15.4"` / `"Android 12"`）在
`wx.getSystemInfoSync()` 与 **`wx.getDeviceInfo()`** 里。

⇒ 基础库 **≥ 2.20.1**（`getAppBaseInfo` 存在）时走上面的**新分支** ⇒ `info.system === undefined`
⇒ `system = ''` ⇒ 三个正则全不命中 ⇒ **`detectGlass()` 无条件返回 `false`**。

### 实证（可复跑）

```
node tools/verify_glass_probe.js --src <PR 分支工作树>
```

| 场景 | 期望 | 实际 | 结果 |
|---|---|---|---|
| S1 iOS 15.4 + 基础库 3.17.3 | `true` | **`false`** | ❌ |
| S2 Android 12 + 基础库 3.17.3 | `true` | **`false`** | ❌ |
| S3 开发者工具（Windows 宿主） | `true` | **`false`** | ❌ |
| **S4 反向对照**：若返回值里**带 `system`** | `true` | `true` | ✅ |
| S5 老基础库（无 `getAppBaseInfo`，走 `getSystemInfoSync`）iOS | `true` | `true` | ✅ |
| S6 / S7 Android 8.1（新旧两条路径） | `false` | `false` | ✅ |
| S8 探测接口全抛异常 | `false` | `false` | ✅ |

**S4 是决定性证据**：只要 `system` 字段存在，行为立刻正确 ⇒ 问题**不是**机型判断逻辑，而是**取字段的接口选错了**。
**S5 说明这是「升级即退化」**：同一台设备，基础库越新反而判成「不支持」，且不报错、不可见。

### 影响

`globalData.glassSupported` 在**所有设备**上恒为 `false`。后续 F11~F19 若按此结果给页面加
`.is-glass-fallback`，则**全端退化为纯白实底 + `box-shadow: none`**（`glass.wxss` 里该分支的规则）
—— F10 的整套「液态毛玻璃」视觉**永远不会出现**，且表现为"样式就是这样的"，不会报错。

⚠️ 严重度说明：**不影响稳定性**（`glass.wxss` 的默认态本身就是安全可读的半透明实底，
CSS 侧有完整的 literal fallback），所以是**功能不可用**而非**界面崩坏**，故为 P1 而非 P0。

### 为什么 PR 描述里的验证没发现

描述写的是「基础库 3.17.3 编译通过 / `glass.js` 正常加载 / `app.js` 正常启动」——
这些只验证了**能加载、不报错**，**没有断言返回值**。本问题恰好是"加载正常、返回值恒假"。
（S3 表明：即使在开发者工具里也不会被发现，因为工具宿主同样走 `getAppBaseInfo`。）

### 修法（已实测有效）

```diff
-    const info =
-      typeof wx.getAppBaseInfo === 'function' ? wx.getAppBaseInfo() : wx.getSystemInfoSync()
+    // system 字段在 getDeviceInfo / getSystemInfoSync 里；getAppBaseInfo 不返回 system
+    const info =
+      typeof wx.getDeviceInfo === 'function' ? wx.getDeviceInfo() : wx.getSystemInfoSync()
```

工具第二节对「只改这一行」的版本实测：F1 iOS → `true`、F2 Android 12 → `true`、
F3 Android 8.1 → **仍为 `false`**（没有过度开启）、F4 老基础库 → `true`。**4/4 通过。**

> 10 秒自查（若对我的结论有疑问，请在真机/开发者工具控制台跑一次）：
> ```js
> console.log(Object.keys(wx.getAppBaseInfo()))   // 期望不含 'system'
> console.log(wx.getDeviceInfo().system)          // 期望形如 'iOS 15.4'
> ```

## 2. P2（不阻断）

### P2-1 · `.is-glass-fallback` / `.is-glass-reduced` 是**祖先选择器**，但小程序无法给 `page` 加 class

```css
.is-glass-fallback .xj-glass, .is-glass-fallback .xj-glass-card, ... { background: #fff; ... }
```

小程序**不能给 `page` 元素设置 class**（`page` 由框架生成，WXML 里也没有可写的根节点），
所以要让上述规则生效，**每个页面都必须自己包一层 `<view class="is-glass-fallback">`**，
并从 `getApp().globalData.glassSupported` 读值算出类名。

实测现状：`miniprogram/pages/` 下 **0 处**引用 `xj-glass` / `is-glass-*`；
`globalData.glassSupported` **只被写、从未被读**。

本 PR 的定位是「只做基础设施」，所以这**不是本 PR 的缺陷**；但接口形状是**不对称**的
（JS 只给一个布尔值，CSS 要一个祖先 class），如果 F11 开工前不定统一消费方式，
20+ 个页面很可能各写一套、且漏做降级。

**建议**：F11 开始前先落一个共享入口（例如 `behaviors/glass.js` 提供 `glassClass` 计算属性 +
约定各页根节点 `class="{{glassClass}}"`），并在方案文档里写明这句约定。

### P2-2 · `@supports` 不在 WXSS 官方文档列举的语法内，需真机验证

WXSS 官方文档「样式导入 / 全局样式 / 渲染引擎对 WXSS 的影响」只明确列了 `@import` 与 Media Query，
**没有列 `@supports`**；且明确写了「**Skyline 渲染引擎对 WXSS 语法有额外限制**」。

利好面：本 PR 的设计是**默认态不依赖 `@supports`**，所以即使 `@supports` 被忽略，
最坏结果只是「不增强为真玻璃」而不是「样式坏掉」—— 这正是它比方案文档原方案更稳的地方（见 P2-3）。

**建议**：F10 合并后，在**至少一台低端 Android 真机**（Android 8/9，WebView 版本旧）
+ 一台 iOS 上各抽测一次，确认玻璃态与降级态的实际观感；结论补进方案文档。

### P2-3 · 与方案文档 §1.2 的分层方向**相反**（PR 的方向更正确，建议改文档）

`docs/二阶段整改方案-前端UI重构与后端支撑.md` §1.2 规定：

```
第一层：现代设备 —— 真毛玻璃      backdrop-filter: blur(20px) saturate(180%);
第二层：不支持 backdrop-filter   @supports not ((backdrop-filter: blur(1px)) or (-webkit-...)) { ... 提不透明度 }
第三层：...
```

即「**默认依赖现代能力，再回头降级**」。而本 PR 有意反向：

```
默认态（基线）：不依赖 CSS 变量 / @supports / backdrop-filter  → 0.86 半透明实底
@supports 命中时（正向增强）：才转 0.62 + blur
```

PR 代码注释里给了理由，**而且这个理由是成立的**：`@supports not` 方案在
「引擎完全不解析 `@supports`」（等于两条规则都不生效，只剩第一层的 0.62 半透明）
时会退化成可读性较差的底色，属于「默认不安」。

⇒ **建议采纳 PR 的方向，并同步修订 §1.2**（团队既有规则：现行方案文档必须与实现一致，
否则下一个人照 §1.2 写会产出**第二套竞争模式**）。

## 4. 值得肯定的地方（8 条）

1. **三重冗余声明**：每个 `var()` 前都先写一条 literal 声明（`background: rgba(...); background: var(--x, rgba(...));`）——
   这是「CSS 变量未定义 / 值非法」时唯一可靠的兜底姿势（注意：自定义属性**已定义但值非法**会走
   "invalid at computed-value time"，**不会**回退到前一条声明，所以前一条 plain 声明才是真保险）。
2. **用 `page` 而不是 `:root`** —— 小程序不支持 `:root`；用 `page` 是正确选择，
   且 `page { --xj-* }` 是**标签选择器**，按官方规则会作用到自定义组件内部（变量能继承进去）。
3. **正向 `@supports` 而非 `@supports not`**，并把这个设计取舍写进了注释（见 P2-3）。
4. **`glass.js` 用能力探测（`typeof wx.getAppBaseInfo === 'function'`）而不是基础库版本号比较** —— 正确姿势。
5. **`detectGlass()` 全函数 `try/catch` 兜底 `false`**，S8 实测通过：探测接口炸了也不会崩。
6. **降级类里把 `box-shadow` 与 `backdrop-filter` 一并清掉**（`.is-glass-fallback { box-shadow: none; backdrop-filter: none }`）——
   避免了"实心底 + 玻璃阴影"的错配；`.is-glass-reduced` 顺带去掉模糊**兼顾性能**，考虑周全。
7. **`app.wxss` 的 `@import` 落在文件最前**（WXSS 要求 `@import` 在最前；且 `@import` 语义是**原地插入**，
   放最前可保证 tokens 先于既有 `page {}` 生效，两者属性无重叠）。`git diff --check` 通过 ✓。
8. **范围克制**：5 文件全在 `miniprogram/`，只新增 + 两处追加，**未动 backend / db / ai，未改写任何既有页面样式**；
   文件头还主动注明了「自定义组件需结合 `styleIsolation` 处理」——这个坑提前写了，很难得。
