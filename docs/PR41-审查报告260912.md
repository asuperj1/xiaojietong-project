## 四、新发现的问题

### [P1] N-01 · 上传签名「只写不读」的闭环缺口（默认开启即会裂图）

- **位置**：生成侧 `backend/app/routers/upload.py:84,89`；校验侧 `backend/app/core/static_safety.py:38-48`；读取侧 `routers/secondhand.py:33`、`routers/favorite.py:52`、`routers/user.py:25`、`routers/auth.py:43`
- **证据**（全仓检索签名使用点，PR head）：
```text
生成点仅 1 处：routers/upload.py:84   access_url = storage.url_for(saved["key"])
校验点仅 1 处：core/static_safety.py:39   if settings.upload_signed_url_enabled: ...
读取侧全部直接返回入库裸路径：
  secondhand.py:33   i["images"] = _parse_json(i.get("images_json", ""))
  favorite.py:52     i["images"] = _parse_json(i.get("images_json", ""))
  user.py:25 / auth.py:43   "avatar": u.get("avatar", "")
```
```python
# config.py:79 —— 默认开启
upload_signed_url_enabled: bool = True
upload_url_ttl_seconds: int = 604800      # 7 天
```
- **影响**：开启签名后，`/static/uploads/*` 必须带 `?e=&s=`，否则 **403**。而：
  1. **列表/详情/收藏/头像**返回的是入库裸路径 → **立刻 403**（图片全裂）；
  2. 即使客户端保存了「上传时返回的签名 URL」，**7 天后也必然 403**（TTL 604800s）；
  3. 当前库里几乎无图片数据（前端 PR39 尚未接上传），所以**现在不炸**；但**前端一接图片上传（规格 §7）就会立刻炸**，且是"上线级"故障。
- **建议（三选一，按成本排序）**：
  1. **最简单**：把 `upload_signed_url_enabled` 默认改为 `False`，并在 `docs/api.md` 注明「启用前需完成读取侧重签名」；
  2. 提供 `storage.resign(url)`：识别 `/static/uploads/` 前缀 → 重新签名（兼容入库的完整路径），在 `secondhand`/`favorite`/`user` 返回图片字段前统一调用；
  3. 长期：图片 URL 由接口**每次实时生成**，DB 只存 key（最干净，但改动面大）。
  > 注：`LocalStorage.url_for(key)` 目前会拼成 `{prefix}/{key}`，若直接传入入库的完整路径会得到 `/static/uploads//static/uploads/xxx.jpg`，**因此方案 2 需要新增函数而非复用 `url_for`**。

### [P2] N-02 · `services/route.py` 的 A\* 缺迭代/规模上限

- **位置**：`backend/app/services/route.py`（`_astar` 的 `while heap` 主循环 + 网格由 `_GRID_M` 计算 `rows/cols`）
- **证据**：全文件未见 `max_iterations` / 迭代计数 / 网格尺寸上限；网格规模 = 起终点包围盒 ÷ 网格粒度
- **影响**：跨校区（数公里）时节点数可达数万，无耗时代价上限；虽是同步函数跑在线程池（不阻塞事件循环），极端入参下仍会长时间占用工作线程
- **建议**：加 `max_iterations` 或「网格边长上限」，超限时回退为直线距离 + 转向估计，并在响应里标注 `approximate: true`

### [P2] N-03 · `tests/test_ratelimit.py` 存在顺序依赖/flaky 风险

- **位置**：`backend/tests/test_ratelimit.py:32-34`
- **证据**：
```python
codes = [client.get("/ping").status_code for _ in range(6)]
assert codes.count(200) == 3, codes
assert 429 in codes, codes
```
- **影响**：限流计数在**进程内存**，与同批次用例共享（`test_health_login` 也会登录、`test_authz_chat` 也会请求）→ 本轮单独实测通过（7 passed），但全量/乱序或有其它登录用例时可能少计 200 而失败
- **建议**：用例内用独立桶（伪造 `X-Forwarded-For` 隔离 IP），或先等待窗口；并把集成用例用 `-m integration` 分组执行

### [P2] N-04 · PR 描述未填写

- **位置**：PR #41 描述体
- **影响**：审查者无法从描述获知动机、范围、自测证据与遗留项；与 PR #39（描述完整、含「已做/未做」双清单）形成明显反差，也破坏 `docs/团队Git合作协议.md` 的模板约定
- **建议**：补写「改动类型 / 实现内容 / 修改模块 / 自测情况 / 注意事项」，其中自测情况建议直接引用本报告的实测数据（`7 passed, 0.66s`）

### [P3] N-05 · `upload_url_secret` 留空时从 `jwt_secret` 派生

- **位置**：`backend/app/core/url_sign.py:20-22`
- **影响**：生产轮换 JWT 密钥会使**所有已发出的签名 URL 立即失效**（TTL 内也失效）；代码注释已提示「生产建议独立配置」，但未强制
- **建议**：把 `XJT_UPLOAD_URL_SECRET` 纳入 `XJT_ENV=prod` 的启动硬校验（与 JWT 密钥同级）

## 五、亮点（建议团队沿用）

1. **`upload.py` 的落库策略正确且注释清晰**：`access_url.split("?")[0]` 入库存**裸路径**、返回客户端**签名 URL**，并注明「避免过期签名入库」。
2. **`url_sign.py` 用 `hmac.compare_digest` 防时序攻击**，且 `max(60, ttl)` 防止 TTL 被配成 0。
3. **`static_safety.py` 校验失败返回统一契约**：`403 + {"code":2003,"message":"资源链接无效或已过期"}`（而不是裸 403 文本）。
4. **`conftest.py` 的「环境不可用则 skip 而非 fail」设计**：保证任何成员机器上 `pytest -q` 都能给出结论，不会因缺扩展/密码而"红一片"。
5. **测试断言用业务码而非 HTTP 200**：`test_authz_chat.py:27` 断言 `code == 1001`、`test_forum_audit.py:43` 断言 `code == 3003` —— 正好规避了本项目 `BizError` 返回 400 的坑。
6. **`notice.py`/`recommend.py` 有明确上限**：`_MAX_NOTICES = 200`、`_CANDIDATE_LIMIT = 200`，避免全表加载后再内存排序。
7. **`storage.py` 用 `Protocol` 定义接口 + 对象存储占位回退本地**：切配置不会导致启动失败。
8. **`99e_poi_seed.sql` 幂等**（指定主键 + `ON DUPLICATE KEY UPDATE`），可重复执行；并诚实标注坐标为示意值。
9. **`requirements.txt` 为未使用的包加说明注释**，消除了「以为已接 Redis/Celery」的误导（虽未删除，但已可接受）。
