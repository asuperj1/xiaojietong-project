## PR #63 · `feat/rag/C15`：切片策略可插拔

**范围**：8 文件 +951/−9（`chunker.py` +252、`test_chunker.py` +335、`chunker_golden.json` +359、`config` +3、`rag.py` +2、2 文档）

### 结论：建议 Approve

**做得好的地方**

1. **不回归的证据链很硬**：默认策略 `fixed` 委托给 `_split_fixed_length`（**逐行保留原实现**），并用**旧实现生成的** `chunker_golden.json`（40 组「文本×尺寸×重叠」）断言新实现**逐字节一致** —— 证明"现有行为不变"而不是口头承诺。
2. **顺带修掉一个真缺陷**：原实现 `chunk_size<=0` 会在 `while len(sent) > chunk_size` 里**死循环**（`sent[:0]` 恒空、`sent[0:]` 恒原串），现抛 `ValueError`（登记 `CAC-26`）。放在空文本检查之后，保持"空输入恒返回 `[]`"的既有语义。
3. 注册表形状与 `C15` 的 rerank / `C16` 的切片一致（`register/get/available/resolve`），可扩展性好；未知策略回退默认 + 告警，不打挂离线索引。

**问题**

- **P3-1（文档缺口）**：`SemanticBoundaryStrategy` 在**段落边界不做重叠** —— `overlap` 参数仅在"某段自身超长、退回 `_split_fixed_length`"时生效。即 `fixed` 有块间重叠、`semantic` 没有。这多半是有意（段落边界清晰、重叠反而制造重复），但 **docstring 未说明这一行为差异**。建议补一句，避免后来人以为两者只差"是否切段"。
- **P3-2（同类参数处理不一致）**：`chunk_size<=0` 抛 `ValueError`，而 `overlap >= chunk_size` 是**静默修正**为 `chunk_size//5`。同类非法参数、两种处理。建议统一（要么都抛、要么都在 docstring 明写"自动修正"）。

## PR #65 · `feat/rag/C20`：引用真实性校验 + 拒答设计实测修正

**范围**：10 文件 +1171/−5（`citation_check.py` +340、`chat.py` +53、`test_citation_check.py` +344、`test_chat_c20_gate.py` +146、前端 `request.js`/`chat.js` 各 +17、`api.md` +11、`tools/verify_citation_check.py` +221）

### 结论：建议 Approve with comments —— **1 条 P2 建议合并前处理**

**做得好的地方**

1. **把"被实测否掉的设计"如实写进代码**：原"文本覆盖率拒答"方案经 27 题实测（正样本 Q23 覆盖率 **0.000**，比两条负样本都低）证明**正负区间完全重叠、不存在可分阈值**，作者据此**改设计**为"只按相似度分数拒答"，并把实测表固化进 `should_refuse` 的 docstring + **回归测试锁定**（`test_lexical_coverage_would_falsely_reject_a_legit_question`）。这是罕见的诚实度。
2. **闸门分级合理**：标记级（`[n]` 越界 / `[标题]` 不匹配来源）是**纯结构校验、可靠**，当门禁；句子级 n-gram 覆盖率**默认关闭**（作者论证它区分不了"改写"与"编造"，只作诊断）。
3. 拒答时**不下发 sources**（否则前端把无关文档当依据展示）；`check_citations` 整块 `try/except`，**校验失败不影响对话**。
4. 落库的是**清洗后文本**（非模型原话），并新增 `citations`/`refused` SSE 事件，前后端契约同步（`api.md §0`）。

**问题**

- **P2-1（建议合并前处理）：`clean_answer` 可能误删 Markdown 链接 / 方括号标记**

  `_CITE_RE = r"[\[【]\s*([^\[\]【】]{1,60}?)\s*[\]】]"` 会提取**任何**方括号内容，`clean_answer` 又会**删除**判定为伪造的标记。三个真实误伤场景：

  | 场景 | 模型输出 | 后果 |
  |---|---|---|
  | Markdown 链接 | `详见[图书馆开放时间](https://lib...)` | `[图书馆开放时间]` 若不匹配来源标题 → **被删**，留下 `(https://lib...)`，链接破坏 |
  | 模仿 prompt 格式 | 知识库文本以 `[分类] 标题: 内容` 喂给模型（`build_system_prompt`），模型可能模仿输出 `[图书馆]` | `[图书馆]` 不匹配**标题** → **被删** |
  | 代码/数字下标 | `arr[0]`、`[1,2]` | 被当引用提取，越界 → **被删** |

  影响：正文被改、链接破坏，且**只打 `warning` 日志**，用户与前端无感。

  **建议**（任一即可）：
  1. 收紧提取——只把**纯数字**（`[1]`）与**能匹配来源标题**的方括号当引用；其余**不提取**（不删）；
  2. 或把 `clean_answer` 从"删除"改为"**只标记 + 告警**"（更保守，符合本模块"宁可放过不可错杀"的自述原则）；
  3. 至少在 `extract_citations` docstring 写明该风险，并加一条"Markdown 链接不被识别为引用"的回归测试。

- **P3-1**：`clean_answer` docstring 说"去掉因此产生的空括号"，实现只清理了空格（因删除的 span 含括号，实际不会留空括号）——**措辞与实现不一致**，无害但易误导。
- **P3-2（已被作者登记的缺口）**：拒答**只在有 `score` 时**生效；关键词降级路径（Ollama/向量库故障）**永不拒答** → 该路径下 `C14` 的"负样本误命中"问题**依然存在**。已登记 `CAC-27`（基线未记 score，阈值无法标定），此处仅作提醒：降级态仍需一道兜底。

## PR #67 · `feat/c26-topic-search`：帖子搜索索引优化（**已合并**）

**范围**：6 文件 +769/−1（`forum_dao.cpp` +93、`19_topic_fulltext.sql` +86、`bench_c26_topic_search.py` +456、`perf-benchmark.md` +118、头文件/绑定 +17）

### 结论：事后审查 —— 设计扎实，2 条改进项

**做得好的地方**

1. 用 **FULLTEXT + ngram** 拿下"1 万条 p95 1.42ms"，附 **bench 脚本 + 性能文档**，可复现。
2. **关键词净化**到位：去掉 boolean 运算符（否则用户输入 `-图书馆` 会变成"**排除**图书馆"，语义反转）+ 空白拆词每词前缀 `+`（AND 语义）+ **词数 8 / 单词 64 字节封顶**（防请求体当放大器）。
3. 三处**契约注释**（检索列序必须与索引同序、`relevance` 只能 SELECT 算不能 WHERE 引用、空关键词退化分页）写在代码里，配合 `19_topic_fulltext.sql` 的部署说明。

**问题（事后改进项）**

- **P3-1（部署风险）**：新增的 `db/sql/19_topic_fulltext.sql` 需**单独执行**。若某环境漏执行，`MATCH(...) AGAINST(...)` 在**无 FULLTEXT 索引**的列上会直接报错（MySQL 1191），而非降级。建议：DAO 侧捕获该异常并**回退 `LIKE`/`page_topics`**，或在启动自检里校验索引存在。
- **P3-2**：检索行为依赖服务器 `ngram_token_size`（本机=2）。换环境若配置不同，命中与排序会变。SQL 文件里已提示，建议在 `perf-benchmark.md` 或部署清单里显式列为**环境前置条件**。
