## 🔴 P0 · `/life/notices` 的过滤是**空操作**，私密行全量泄漏

`routers/life.py`：
```python
rows = cpp_bridge.life_dao().page_notices(page, size, category, target_grade)
rows = [r for r in rows if not is_private_audience(r.get("target_grade"))]
```
`db/cpp_driver/src/dao/life_dao.cpp`：
```cpp
"SELECT id, title, content, source, category, publish_time "   // ← 没有 target_grade！
"FROM campus_notice WHERE ... ORDER BY publish_time DESC LIMIT ? OFFSET ?"
```

**只读探针实测**（真实 MySQL + 真实 `jt_db`）：
```
① DAO 返回列 = ['category','content','id','publish_time','source','title']
   含 target_grade 吗 = False
   r.get('target_grade') = None
   is_private_audience(该值) = False
   → life.py 的列表推导会剔除这一行吗 = 不会（过滤是空操作）
② 对照（函数本身没问题）：
   is_private_audience('__push:reminder:12:D7') = True
   is_private_audience(None) = False
```

`target_grade` **不在 SELECT 里** ⇒ `r.get("target_grade")` 恒 `None` ⇒ 判断恒 `False` ⇒ **一行都不会被剔除**。

**影响**：B18 上线后，个人待办推送（标题形如「【还有 7 天】截止 …」）会返回给**任何登录用户** —— 与已修的 `DATA-01` 同级。

## 🔴 P0/P1 · 为什么"实测零泄漏"是假绿：两条断言都是**恒真的空断言**

**① `tests/test_notice_push.py:68`**
```python
assert not notice_scheduler.is_private_audience(item.get("target_grade"))
```
`item` 来自 API 响应，而**响应里没有 `target_grade`** ⇒ `.get()` 是 `None` ⇒
`is_private_audience(None) = False` ⇒ `assert not False` ⇒ **恒真通过**。

**② `tests/verify_b16_b18.ps1:192`**
```powershell
$leak = @($pub.data.items | Where-Object { $_.target_grade -like "__push:*" })
```
`$_.target_grade` 不存在 ⇒ `$null -like "__push:*"` = `False` ⇒ `$leak.Count = 0` ⇒ **恒真通过**。

**③ 叠加巧合**：实测 `campus_notice` 共 10 行、**私密行 = 0**（已回收干净）⇒ 即使断言写对，在零私密行数据上也会通过。
两个原因叠加，导致"零泄漏"从未被真正验证。

> 📌 建议加一条团队规约：**断言必须依赖一个"有缺陷时必然为真"的可观测事实**。
> 正确写法（任选）：① 把私密行**标题**当已知串断言不出现（最直观）；② 调度前后 `/life/notices` 的 **id 集合差量**；
> ③ 先 `assert "target_grade" in items[0]`（字段存在性前置）。
> 这与本仓既有的「jt_db 字符串化导致断言假通过」是**同一族问题：断言依赖的东西不存在**。

**修法**（必须同时解决分页口径）：不要在 Python 侧过滤（**拿不到列就永远过滤不了**）。照 `notice.py::_visible_notices` 把
`target_grade NOT LIKE '__push:%'` **下推到 SQL**，并用同条件 `COUNT(*)` 算出正确 `total`；`is_private_audience` 在 `life.py` 的用法应删除。
（给 DAO 加参数需重编译 C++，与本 PR「无需重编译」的声明冲突 → 建议并入下一批。）

## 🔴 P1 · `POST /admin/knowledge/purge`：LIKE 通配符未转义 → 一条调用清空知识库

`knowledge.py`：`source_url LIKE ?` + `[f"{p}%"]`，而 `p` 只做了 `strip`/替换反斜杠/截断，
**没有转义 `%` 与 `_`** ⇒ 传 `source_prefix = "%"` 时 `LIKE '%%'` **匹配全部文档**（`"_"` 同理）。
`admin.py` 的守卫只有 `if not body.source_prefix.strip(): raise err_param(...)` ⇒ **`"%"` 能通过**。

⇒ 一次管理端调用删除**全部** `knowledge_doc` + `knowledge_chunk` + 向量（`purge_vectors` 默认 `True`），
**无强制 `dry_run`、无二次确认、无最小长度、不可回滚**；CLI 的 `--purge-source-prefix` 同样风险。

**建议**（建议全做）：① 拒绝含 `%`/`_`/`\` 的前缀；② 最小长度（如 ≥4）；③ 加 `confirm`，未确认时**只返回 `matched` 与候选 id 预览**（CLI 加 `--yes`）；④ 用 `ESCAPE` 或改 `LOCATE(?, source_url) = 1` 做前缀匹配。

## 🟡 P2

1. **`pytest` 声明 45 passed，实测 `2 failed / 66 passed`**（真实 DB + 真实 `jt_db`）：
   ```
   FAILED tests/test_notice_push.py::test_dispatch_d7_push_is_idempotent_and_recoverable
   FAILED tests/test_notice_push.py::test_purge_private_reports_counts
   E  {"code":2003,"message":"需要管理员权限"}   assert 403 == 200
   ```
   两个用例用 **`hdr_a`（普通用户）** 调 `GET /admin/notices/pending`、`POST /admin/notices/purge-private`；
   `get_current_admin` 判 `role >= 1` 正常拦截。本 PR 对 `conftest.py` 的改动只有「口令回退读 `.env`」，
   **没有管理员夹具** ⇒ **干净环境 / CI 上必挂**（描述里的 45 与当前 68 个用例数也不符）。
   → 建议加 `admin_a` 夹具，两个用例改用它；描述数字更新为实测值。
2. **上传解析通道先整体缓冲、后判上限**：`await upload.read()` 整包进内存，`parse_bytes` 里才判 32MB。
   而同仓 `upload.py:51` 的注释**恰好写明了这个坑**并有 `_read_limited()` —— 新通道未复用。
   建议把 `_read_limited` 提到 `core/` 共用。
3. **PDF 解压上限在 `zlib.decompress()` 之后才判** ⇒ 解压炸弹在判之前已分配内存。
   容错分支（`line 221`）已在用 `decompressobj()`，建议主路径也传
   `max_length=_MAX_STREAM_BYTES`。（其余护栏对：`_MAX_STREAMS=512`、**无 XML/DTD 解析 ⇒ 无 XXE 面**。）
4. **过滤放在分页之后** ⇒ `total` 失真 + **公共行不可达**（DAO 按 `publish_time DESC` 取窗口，**不会因过滤补位**）；
   私密行每天新增（`MAX_ITEMS=500`）量上来后 `page=1` 可能几乎为空。修 P0 时一并下推到 SQL。
