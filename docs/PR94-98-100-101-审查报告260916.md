## 🔴 核心发现：`deadline` 归一化**三份实现、口径已经漂移**

同一件事（判断两个 deadline 是否同一日期）在三处各写了一遍：

| 位置 | 实现方式 |
|---|---|
| `#98` `ai/dataset/quality.py::normalize_deadline` | 取前 10 字符（只认 `-`） |
| `#94` `ai/eval/extract_bench.py::normalize_deadline` | 正则认 `-` / `/` / `年月日` + 补零 |
| `#100` `backend/app/services/notice_extract.py` | 完整解析器，返回 `datetime` |

而 `#94` 的 docstring 明确写着「**与 C32 的 `normalize_deadline` 同一口径**」——
即一致性是靠**复制粘贴**维持的，没有共享实现、也没有对照测试。

### 实测：10 组输入有 5 组结果不同

| 输入 | C32 输出 | C34 输出 | |
|---|---|---|---|
| `'2026-09-30'` | `'2026-09-30'` | `'2026-09-30'` | ✅ |
| `'2026-09-30 23:59:59'` | `'2026-09-30'` | `'2026-09-30'` | ✅ |
| `'2026-09-30T10:00:00'` | `'2026-09-30'` | `'2026-09-30'` | ✅ |
| `'下周三'` | `'下周三'` | `'下周三'` | ✅ |
| `'不是日期'` | `'不是日期'` | `'不是日期'` | ✅ |
| **`'2026/9/30'`** | `'2026/9/30'` | `'2026-09-30'` | ❌ |
| **`'2026年9月30日'`** | `'2026年9月30日'` | `'2026-09-30'` | ❌ |
| **`'2026-9-3'`** | `'2026-9-3'` | `'2026-09-03'` | ❌ |
| **`'无'`** | `'无'` | `None` | ❌ |
| **`None`** | `''` | `None` | ❌ |

### 影响（这是本报告最需要关注的一条）

- **C32 口径过严**：`'2026/9/30'` 与 `'2026-09-30'` 会被判**不一致** ⇒
  Kappa 被**低估** ⇒ 可能得出"标注质量不达标"的**错误结论**。
  而 C32 的验收标准正是 `Kappa ≥ 0.8`，这个偏差直接影响验收判定。
- **C34 口径过宽**：同样两个值被判一致 ⇒ F1 偏高。
- ⇒ **同一份标注数据，两个任务得出相反方向的偏差**。

### 建议修法（需确认，因为它会改变已有 Kappa 数值）

1. **统一到宽松口径**（认 `-` / `/` / `年月日`、补零、`None -> None`）——
   因为 C32 的目的是"判断两人标的是不是同一个日期"，宽松更贴近意图；
2. 因 `ai/` 与 `backend/` 是两个目录、共享成本高，**至少加一条跨模块对照测试**
   （同一组输入喂两处实现，断言输出一致），把"靠复制粘贴保持一致"变成"靠测试锁死一致"；
3. `#94` 的 docstring 若要保留"同一口径"的措辞，就必须有第 2 条兜着；否则改为如实描述差异。

> 这条正是刚在 C31 学到的那句话的延续：**修/写一处时，要问"同一件事还有几处实现"**。
> 我在 C31 修 `str(None)` 时只看了 C31 自己，没横向扫 C32/C34 —— 这次扫出来了。
