## 2. 根因定位（证据链，置信度已标注）

```
.github/workflows/ci.yml:60   run: bash db/cpp_driver/scripts/build.sh        ← 失败的就是这一步（exit 2）
        ↓
db/cpp_driver/scripts/build.sh 头部注释：需安装 gcc/g++、cmake、libmysqlclient-dev、python3-dev、pybind11
        ↓
db/cpp_driver/CMakeLists.txt:35
   find_package(Python 3.8 COMPONENTS Interpreter Development REQUIRED)        ← 要求 Python 的 **Development** 组件
        ↓
.github/workflows/ci.yml:80-82
   sudo apt-get install -y -qq cmake g++ libmysqlclient-dev mysql-client      ← 🔴 **没有 python3-dev**
```

- **置信度：高（静态推断已闭环），但尚未看到该步骤的原始日志。**
  请先按 4.0 取一次日志确认（大概率会看到
  `Could NOT find Python3 (missing: Python3_INCLUDE_DIRS Python3_LIBRARIES Development ...)` 或
  `CMake Error at CMakeLists.txt:35`）。
- **已排除的假设**：脚本行尾（CRLF）—— 仓库有 `.gitattributes` 且写了 `*.sh text eol=lf`，
  我在 git 里核过 `build.sh` 是 **纯 LF**（0 个 CR 字节），所以不是它。
- **顺带说明**：`actions/setup-python` 装的 CPython 通常带 `include/` 但**不带 `libpython*.so`**，
  而 CMake 的 `Development` 组件同时要求"头文件 + 库"（等价于 Embed），
  所以"装了 setup-python"并不能替代 `python3-dev`。

## 4. 建议的改法（请你做，我不动）

### 4.0 先取一次失败日志，把根因钉死
在 GitHub 上打开任一次失败运行 → 点 job `G1 · pytest（后端）` → 展开第 7 步，
或直接用 API（附录 A 的第 2 条）。**先确认是不是缺 `python3-dev`**，再改。

### 4.1 补构建依赖（两条都做最稳）
- **apt 行加 `python3-dev`**（与 `build.sh` 的注释声明保持一致）；
- **CMake 侧把要求收窄**：`find_package(Python 3.8 COMPONENTS Interpreter Development REQUIRED)`
  → 只保留 **`Development.Module`**。我们编的是 **Python 扩展模块**，不需要 Embed（不需要 `libpython.so`）。
  这是既有代码的问题（#104 没动它），但既然编译在 CI 上过不去，顺手一起收窄最省事。

### 4.2 让编译失败**可诊断**
现在的失败只给一个 `exit code 2`，看不出是缺依赖还是配置错。
建议在第 7 步把输出留全（例如失败时 `cat db/cpp_driver/build/CMakeFiles/CMakeError.log`，
或 `bash db/cpp_driver/scripts/build.sh 2>&1 | tail -60`）。
**理由**：CI 的失败信息本身就是给别人看的文档；一个"只报退出码"的步骤，下一个人还得从头查一遍。

### 4.3 收敛触发范围
`on.push.branches` 去掉 `"feat/**"` / `"fix/**"`，只留 `dev`、`main`；
分支上的验证交给 `pull_request`（已经有了）。这样：分支 PR 仍会被检查，但不会每次推送都全量跑两遍。

### 4.4 补一条"门禁自证"（**这条最重要**）
门禁跑通之后，请**故意制造一次失败**并确认它真的变红，例如：
- 让 `rag_bench` 的题目集为空、或
- 临时把某个 pytest 用例改成 `pytest.skip`（你的 `--strict` 语义是"skip 即红灯"，正好可验）

**为什么必须做**：否则我们永远分不清**"门禁通过"**和**"门禁没跑"** —— 这正是本仓库反复踩过的
"假绿"坑（`--strict` 的设计意图就是治它，那就得让它先自证一次）。
建议把这次自证的记录（截图或运行链接）写在 `docs/CI.md` 里。

## 5. 如果你判断应该整体撤回（备选，我不反对）

我已在本地**演练过**，结论：**技术上干净**。

```bash
git revert -m 1 a443a4c      # 演练结果：EXIT=0，无冲突
# 影响文件：
#   D  .github/workflows/ci.yml
#   D  docs/CI.md
#   D  tools/ci_gate.py
#   M  ai/eval/rag_bench.py      ← 回退为没有 --strict 的版本
```

但有三个代价，写在这里供你权衡：
1. **会一起撤掉有价值的部分**：`tools/ci_gate.py` 的"skip 即红灯"、`rag_bench --strict` 的防假绿，
   设计意图是对的，只是**没跑起来**；
2. **"撤销合并提交"有后遗症**：这条分支以后想重新合入，得**先把这次 revert 再 revert 掉**，
   否则 git 认为它已经合过了；
3. **流程上仍要走 PR**：`dev` 受 `team-branch-protect` 保护（要 PR + 至少 1 个 approve，
   **作者不能自批**），所以撤回也不能直推 `dev`。

⇒ 我的建议仍是 4.1~4.4 的 fix-forward；**除非**你觉得后面还藏着第二个、第三个 bug
（这个担心是合理的，因为门禁从未跑过），那就先撤回、把新工作落到一个干净的 PR 里。

## 7. 哪些**不是**你的锅（免得白改）

- `db/cpp_driver/CMakeLists.txt` 与 `scripts/build.sh` **都是既有文件**（#104 只动了 4 个文件：
  `ci.yml`、`ci_gate.py`、`docs/CI.md`、`rag_bench.py`）。编译依赖缺项是**新工作流**没把环境配齐，
  不是那两个文件写错了。
- **`--strict` 的设计方向是对的**，我认同"宁可红灯，不要假绿"这个原则 —— 本仓库确实有
  `pytest.skip` 导致的假绿风险，你把它收口到 `ci_gate.py` 的思路我赞成。这次要修的只是
  **让它先能跑起来**。

> 最后一句流程面的建议（不是针对你）：**CI 类改动，最好先在作者自己的分支上跑绿、把运行链接贴进 PR 再请人合**。
> CI 的独特之处是"它自己能证明自己"，而我们这次是先合进 `dev` 才第一次跑 —— 于是 22 次运行全红，
> 既没起到门禁作用，也让大家白看了 22 次红。下次把"绿灯链接"作为合并的前置条件即可。
