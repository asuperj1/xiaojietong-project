## 2. 并发性审计

### 2.1 现状事实

| 项 | 值 | 证据 |
|---|---|---|
| 连接池 | min=2 / **max=16**，获取超时 **5s** | `connection_pool.cpp:12,33`；`config.py:21-22` |

| 空闲回收 | `prune_idle()` **定义但全仓零调用** | `connection_pool.cpp:142` |

### 2.2 🔴 CON-01（P0）· 连接池 16 vs 线程池 40，无背压

```
并发 40 个同步请求 → 40 个 AnyIO 工作线程
                    → 只有 16 条 DB 连接
                    → 第 17~40 个线程 cv_.wait_for(5s)
                    → 超时抛 DbException → pybind → RuntimeError → HTTP 500
```
**证据**：`config.py:21-22`、`connection_pool.cpp:33,68-71`、`main.py`（无 `limit_concurrency`）
**放大效应**：`cpp_bridge.query/execute` **每次调用独立 acquire/release**（`db_session.cpp:11-14`），一个请求发 5 条 SQL 就争抢 5 次。
**修复**：① `max_conn ≥` 线程池上限（如 32）；② 或加 `asyncio.Semaphore` / `limit_concurrency` 背压；③ 把 `ping()` 移出互斥区。

### 2.3 🔴 CON-02（P0）· `Transaction.__del__` 跨线程解绑（thread_local 清错线程）

`__del__` 无条件调 `release_txn()` → `DbSession::clear_txn()` 清的是 **GC 当前线程**的 `thread_local`，而非事务所属线程。
**证据**：`pybind_wrapper.cpp:159-162`、`db_session.cpp:9,20-21`
**后果**：工作线程复用时，A 线程的事务被 B 线程 GC 解绑 → A 后续 SQL **静默脱离事务**（写入 autocommit）；或 B 自身合法事务被误清。
**修复**：`Transaction` 记录创建线程 id，`clear_txn` 前比对。

### 2.4 🟠 CON-03（P1）· 事务块位于 `async def` / 同步 DB 阻塞事件循环

| 位置 | 风险 |
|---|---|
| `rag.py:167-182`（`async def index_doc` 内 `with begin()`） | 当前块内无 `await` 故未出错；**一旦加入 `await`，事件循环线程上其他协程的所有 SQL 会被静默并入该事务** |
| `rag.py:44`（`async def` 内同步 `cpp_bridge.query`） | **直接阻塞事件循环**（见 CAC-01） |
| `agent.py:53`（async 端点直接调同步 `execute_calls`） | 阻塞事件循环 + 事务绑定在事件循环线程 |

**修复**：事务/DB 代码统一移入同步函数，async 端点经 `asyncio.to_thread` 调用；建立约定「**事务块内禁止 `await`**」。

### 2.5 🟠 CON-04（P1）· `like_count` / `comment_count` 与明细表不一致

`toggle_like` 只写 `like_record`，**从不更新 `topic.like_count`**；`add_comment` 的 INSERT 与计数自增**不在同一事务**。
**证据**：`forum_dao.cpp:46-58`（无 like_count 更新）、`forum_dao.cpp:44-53`（无事务）
**后果**：点赞接口返回的 `like_count` 恒为旧值；热度排序（`forum_dao.cpp:83`）失真。
**修复**：同连接同事务内更新计数。

## 3. 事务隔离审计

### 3.1 🔴 TXN-01（P0）· 座位预约可双重预订

**链路**：
1. `library.py:54-61` 事务内 `SELECT COUNT(*)` 做时段重叠校验 → **非锁定快照读**
2. `library.py:62` 裸 `INSERT seat_reservation`
3. `seat_reservation` **无任何 UNIQUE KEY**（`04_library.sql:65-68` 仅 3 个普通 `KEY`）

**为什么快照读救不了**：MySQL 默认 **REPEATABLE READ**，两个并发事务各自读到 `c=0` → 都 INSERT 成功。
**证据**：`library.py:52-63`、`library_dao.cpp:68-77`、`04_library.sql:65-68`
**同一缺陷复制于**：`agent_executor.py:246-259`（Agent 工具路径）
**修复**：
- ① 校验改 `SELECT ... FOR UPDATE`（需在 `library_dao.cpp` 新增锁定查询）；
- ② 或引入固定时段槽位 + `uk_seat_slot` 唯一键；
- ③ 兜底 `INSERT ... SELECT ... WHERE NOT EXISTS`。

> 注：区间「不重叠」**无法用唯一键表达**，必须依赖行锁或串行化隔离。

### 3.2 🔴 TXN-02（P0）· 二手订单可重复成交 / 超卖

`secondhand.py:163-172`：`INSERT secondhand_order` + `UPDATE secondhand_item SET status=1 WHERE id=?`
- `UPDATE` **缺 `AND status=0`** → 不校验当前是否在售
- `secondhand_order` **无 `UNIQUE(item_id)`**（`05_secondhand.sql:61` 仅 `idx_item`）
- `create_order`（`secondhand_dao.cpp:63-71`）不校验状态

**后果**：N 个买家并发下单 → N 张订单；物品状态被反复覆盖。
**修复**：`UPDATE ... WHERE id=? AND status=0` 后用 `affected` 判断，为 0 则回滚；对 `item_id` 建唯一键或加乐观锁 `version`。

### 3.3 🟠 TXN-03（P1）· `favorite` / `like` 并发 toggle → 唯一键冲突 → 500

- `favorite.py:69-72` 在**事务外**先查 `existed`，`:73` 才开事务 → 经典 TOCTOU
- `forum_dao.cpp:46-58` `toggle_like` 查后插，无冲突捕获
- 两表都有 `uk_user_target`（`07_forum.sql:57,70`），并发双击 → 第二个 INSERT 抛 `DbException` → pybind 转 `RuntimeError` → **500**

**对比正确范例**：`job.py:53-56` 是**全仓唯一**正确捕获唯一键冲突的写法（`except RuntimeError → BizError(3002)`）。
**修复**：统一采用 `job.py` 范式；`favorite` 的判断移入事务内。

### 4.1 🔴 SEC-01（P0）· JWT 默认弱密钥硬编码

```python
# backend/app/core/config.py:24
jwt_secret: str = "xjt-dev-secret-change-me"
```
- 无启动校验、无告警、无长度/熵检查
- 攻击者可 `jwt.encode({"uid":1,"role":2,"type":"access"}, "xjt-dev-secret-change-me")` **直接伪造超管 token**

**修复**：默认值改空 + `@model_validator` 在非 debug 且密钥为空/等于已知弱值时**拒绝启动**。

### 4.2 🔴 SEC-02（P0）· 微信登录降级后门

```python
# backend/app/routers/auth.py:48-51
if not settings.wx_appid or not settings.wx_secret:
    return "oXJT_DEV_" + code          # ← 无任何真实性校验
```
- 两个配置默认均为 `""` → **默认部署即降级**
- 任何非空 `code` 都能换出确定性 openid → 自动建号并**立即签发合法 token**
- 无 warning 日志，运维无法察觉
- 若受害者曾用可猜 code（如 `test1`，见 `tests/verify_b2.ps1:18`）登录 → **账号接管**

**修复**：非 debug 模式禁止降级（503）+ 打 WARNING + `/health` 暴露 `auth_mode`。

### 4.3 🔴 SEC-03/04（P0）· 聊天会话 IDOR（两处）

| 端点 | 问题 | 证据 |
|---|---|---|
| `GET /chat/conversations/{conv_id}/messages` | **无归属校验**（仅 `WHERE conversation_id=?`）→ 遍历整数 id 即可**读取任意用户全部 AI 对话** | `chat.py:131-137` |
| `POST /chat/send`（传 `conversation_id`） | 无归属校验 → 可**写入他人会话**，并把他人历史送入模型（提示注入复述） | `chat.py:39-48` |

### 4.4 🔴 SEC-05（P0）· 任意用户可下架他人商品

```python
# backend/app/routers/secondhand.py:168-171
"UPDATE secondhand_item SET status = 1 WHERE id = ?",   # ← 无 user_id 条件
```
- 任意登录用户可把**任意他人商品**标记为「已售」→ 业务 DoS
- 同行 `seller_id`（`:158`）与 `amount`（`body.amount`）**由客户端传入** → 可嫁祸、可 0 元下单
- 未校验物品存在/在售

**修复**：服务端反查 `secondhand_item` 取真实 `user_id`/`price`；`UPDATE ... AND status=0` 后判 `affected`。

### 4.5 🔴 SEC-06（P0）· 账号禁用校验是死代码（本次审计新发现）

```python
# backend/app/core/deps.py:27-28
if user.get("status") == "1":        # 永远为 False
    raise err_forbidden("账号已禁用")
```
**根因**：`user_dao.cpp:17-20` 的 SQL **不取 `status` 列**：
```cpp
"SELECT id, openid, nickname, avatar, phone, role FROM `user` WHERE id = ?"
```
pybind 只转换 SQL 取出的列（`pybind_wrapper.cpp:101-114`）→ `user.get("status")` 恒为 `None`。

**后果**：
1. 管理员禁用/软删用户后，**其 token 与 refresh 全程继续可用**；
2. 同一 SQL 不过滤 `is_deleted=1` → 软删用户照样登录；
3. **副作用（功能层）**：`/user/me`（`user.py:20-31`）与 `/life/notice-feed`（`life.py:106-108`）读取的 `grade/major/campus/student_no/status` **均不在 SELECT 内** → **永远返回空专业/年级/校区，按年级的通知过滤永远失效**。

**修复**：`find_by_id`/`find_by_openid` 补 `status, is_deleted, grade, major, campus, student_no` + `WHERE is_deleted=0`；重编译并补断言。

## 5. 缓存与缓存穿透审计

### 5.1 缓存现状盘点（核心事实）

| 设施 | 状态 |
|---|---|
| 应用级缓存 | **全仓仅 1 处**：`embedder.py:37` 的 `dict`（**无上限、无 TTL、无淘汰、无锁**） |
| Redis / Celery | `requirements.txt:15-16` **声明但零代码使用** |
| `lru_cache` / `TTLCache` / `cachetools` | **0 命中** |
| `Cache-Control` / `ETag` / 条件请求 | **0 命中** |
| DB 查询结果缓存 | 无 |
| `MYSQL_STMT` 复用 | **无** —— 每次调用 `stmt_init + prepare + execute + close` |
| 限流 | **无** |

**内存量级测算**：bge-m3 1024 维 → 每条 `list[float]` ≈ **32 KB**；10 万条不同文本 ≈ **3.2 GB** → 无界缓存是可触发的 OOM 路径。

### 5.2 🔴 CAC-01（P0）· RAG 降级把压力全转 MySQL，并阻塞事件循环

**五步证据链**：
1. Ollama 失败 → `embedder.py:92-93` 记 `_last_fail_at` 并 `return None`
2. 冷却 30s 内 → `embedder.py:72-73` 直接 `return None`（**快速失败，不排队**）
3. `rag.py:75-84` → `emb is None` → **降级 `_keyword_retrieve`**
4. `rag.py:31-50` → 5 组 `(title LIKE '%x%' OR content LIKE '%x%')` 打 **`knowledge_doc.content`（LONGTEXT）全表扫**；且 `rag.py:44` 是**同步阻塞调用写在 `async def` 里** → **阻塞事件循环**
5. 入口：每次 AI 对话都触发（`chat.py:59`）

**结论**：
- 冷却期内**所有对话请求** → 每请求 ≥5 倍 LONGTEXT 全表扫
- 连接池上限 16 + 5s 获取超时 → **AI 故障升级为全站雪崩**（连论坛/二手等无关接口也被拖垮）
- 冷却到点**无 half-open 探测、无并发闸门** → 积压请求**同时打向 Ollama（惊群）**

**修复（无需 Redis）**：
① `rag.py:44` 改 `asyncio.to_thread(...)`（立刻消除事件循环阻塞）；
② 降级路径加独立熔断 + `asyncio.Semaphore(2)` 闸门；
③ 检索结果加进程内 `TTLCache(maxsize=1000, ttl=300)`；
④ 熔断恢复加 half-open 探测。

### 5.3 🔴 CAC-02（P0）· 无空值缓存 → 不存在的 ID 每次穿透

**探测路径**：`forum.py:98`、`job.py:37`、`life.py:86`、`agent.py:127`、`map_api.py:92`、`favorite.py:44` —— 全部「查库 → 没查到 → 抛 1001」，**无任何 negative cache / 布隆过滤器**。

**后果**：脚本枚举 `/topics/999999` 等 → **100% 命中 DB**，且**全站无限流** → 低成本打垮。

**修复**：新增 `services/cache.py`（`TTLCache(maxsize=2000, ttl=30)`）做 negative cache，在抛 `BizError` 前写 `None` 哨兵；同一装饰器顺带缓存命中的结果。

### 5.4 🔴 CAC-03（P0）· `GET /topics/{id}` 每次读都写库

`forum.py:118` 无条件 `UPDATE topic SET view_count = view_count + 1`：
- 热点帖详情 = **同一行排他锁串行**（读操作持有行锁）
- 单请求 **4 读 + 1 写**（`:91,100,106,111,118`）
- 无节流 → 浏览量可被无限刷，热度算法可被操纵

**修复**：`view_count` 改进程内计数器 + 阈值/定时批量 flush；详情主体加 `TTLCache(ttl=10~30)`。

### 5.5 🔴 CAC-04（P0）· 无 single-flight → 热点 key 并发重复回源

| 回源点 | 保护 | 证据 |
|---|---|---|
| RAG 检索 | ❌ 无（同一问题并发 N 次 = N 次 embedding + N 次向量检索） | `rag.py:67-84` |
| embedding 缓存未命中 | ❌ 无（检查→计算→写入非原子，`await` 可交错） | `embedder.py:78-95` |
| 用户身份 | ❌ 无（**每个已认证请求都 `find_by_id` 回表**，JWT 已含 uid/role） | `deps.py:27` |
| Agent 工具 schema | ❌ 无（每个 Agent 任务都查 `agent_tool`） | `agent_executor.py:48-56` |

**修复**：实现 `services/singleflight.py`（`dict[key] → asyncio.Future` + `Lock`），同 key 只放行一次。

### 5.6 🟠 CAC-05（P1）· 无索引覆盖的查询（即使加上 C7 的 11 个索引仍存在）

## 9. 结论

> **校捷通的技术底子比多数学生项目扎实**：C++ 数据层分层清晰、预处理语句全覆盖、
> 事务 RAII 异常安全、SQL 注入面为零、`/admin/*` 鉴权全覆盖、唯一键兜底在多处正确使用。
>
> **但存在「演示即暴露」的系统性短板**，集中在三类：
> 1. **安全边界未收口** —— 弱密钥默认值、认证降级后门、会话 IDOR、越权下架、禁用校验死代码；
> 2. **并发正确性依赖「幸运时序」** —— 关键业务是「快照读 + 先查后写」，**数据库层零兜底**，已确认可双订/超卖；
> 3. **缓存与热点零防护** —— 全仓仅 1 处无界缓存，无空值缓存/单飞/限流，**RAG 降级会把 AI 故障放大为全站雪崩**。
>
> 上述三类问题的共同特征是：**功能测试全绿，但在并发、异常、恶意输入下会失效**。
> 建议按 §7 分三阶段闭环，其中 **阶段一的 8 项（P0）是「敢让评委点」的前提**。
