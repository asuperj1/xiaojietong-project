## 🔴 C8 · 修复 `LAST_INSERT_ID()` 跨连接 bug（P0 · 下次）

**问题**：`backend/app/routers/forum.py:155` 在 `with cpp_bridge.begin()` **之外**执行 `SELECT LAST_INSERT_ID()`。
而 `query()` 会从连接池取**另一条连接** → 拿到 0 或别人的 id，**举报接口返回值不可信**。

**产出**
1. C++ 侧提供安全取值入口：`execute()` 已返回 `(affected, last_insert_id)`，统一封装为"同连接取值"的调用方式（或 pybind 增加 `execute_returning_id`）；
2. **全仓排查同类问题**（事务外取 `LAST_INSERT_ID`、事务内混用池连接）；
3. 与成员2 协作修正 `forum.py` 举报接口。

**验收**：举报后返回的 `report.id` 与库内实际自增 id **一致**；补一条回归用例。

## 🔴 C9 · C6 压测深化 + C++ 侧优化（P0 · 性能翻盘）

**问题**：当前 `0.47x / 0.60x` 的结论源于**场景选错**（单线程 + 单表 27 行 + 极小结果集），
恰好避开了连接池与预处理语句的收益区。这份数据如果端上答辩，是**负资产**。

**产出**
1. **压测脚本扩展**（`db/cpp_driver/test/bench_dao.py`）：
   - `--threads N`：并发 1 / 4 / 8 / 16
   - `--rows N`：造万级测试数据（如 `secondhand_item`）
   - 新增场景：**批量插入**、事务提交/回滚、多表 JOIN、大字段（TEXT/JSON）读取
2. **C++ 侧优化**：
   - `MYSQL_STMT` **句柄复用**（按 SQL 指纹缓存 prepare 结果，避免每次 `stmt_init/prepare/stmt_close`——这是当前"准备开销 > 收益"的直接来源）
   - 新增**批量 API** `execute_many(sql, rows)`（一次往返写多行）
   - 减少 pybind11 转换次数（如一次返回多行）
3. **更新 `docs/perf-benchmark.md`**：保留原基线 + 新增「并发对比表」「万级数据对比表」「优化前后对比表」

**验收**：并发 8/16 场景下 jt_db **QPS 反超** pymysql；万级表分页查询有明确优势；报告含优化前后对比。
