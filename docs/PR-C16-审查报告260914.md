## 三、值得保留的设计（审查中确认无误）

| # | 设计 | 为什么重要 |
|---|---|---|
| 1 | `NoopStrategy` override `rerank` 直接返回，不走基类排序 | 即使日后有人改基类排序逻辑，也不会波及默认路径 |
| 2 | 重排放在 `_retrieve_uncached()` **内部** | 若放在 `retrieve()` 外层，缓存里存的是**未重排**结果，改策略要等 TTL、缓存命中时根本不重排——这个坑踩得很准 |
| 3 | `sorted(key=(-score, i))` 同分保持原序 | `CAC-04` 检索缓存下，否则同一问题两次请求顺序"看起来随机" |
| 4 | `resolve_reranker` 未知名字**回退默认 + WARNING**，不抛异常 | 配置写错不打挂对话；但留 warning 避免"以为开了其实没开"静默很久 |
| 5 | 注册表重名默认抛错 | 防止两人各写一个 `lexical` 互相覆盖 |
| 6 | `lexical` 单文档 `score()` 退化已文档化 | 明确告知"单文档时 IDF 是常数"，不误导调用方 |
| 7 | 评测脚本自曝两个方法学局限（`hit@3` 饱和、只测下界） | 不把"下界"当"收益"报 |

## 四、问题清单

### P0（阻断）：无

未发现正确性缺陷、越权、数据破坏或与架构铁律冲突的问题。

### P2-1（建议合并前修，成本 1 行）：`lexical` 是**已知负收益**，却可被静默启用

**现象**：`resolve_reranker()` 只在**未知名字**时打 WARNING。而 `lexical` 是已注册的合法名字 ——
一旦有人（或日后误操作）把 `XJT_RAG_RERANK=lexical` 写进配置，服务会**静默启用一个已实测降低
`hit@1`（0.92→0.88）的策略**，且日志里没有任何提示。代码里"不得作为默认开启"的约束只写在
docstring 里，**运行时无强制、无警告**。

**建议**：在解析到已知负收益策略时补一条 WARNING，把 docstring 的约束变成运行时可见：

```python
# rag.py 或 rerank.py
_RERANK_PENALTY_WARN = {"lexical"}  # 已实测负收益，启用须显式知情

# resolve_reranker() 命中后：
if strat.name in _RERANK_PENALTY_WARN:
    logger.warning(
        "重排策略 %r 实测为负收益（hit@1 0.92→0.88，见 tools/eval_rerank.py）；"
        "仅用于机制演示，不建议线上启用。", strat.name,
    )
```

> 定级说明：这不是"逻辑写错"，而是**安全网只写在了注释里**。成本极低，建议随本 PR 带上。

### P2-2（建议，不阻断）：`retrieve()` 缓存 key 不含重排策略

`retrieve()` 的缓存 key 为 `(question.strip().lower(), top_k)`，**不含 `settings.rag_rerank`**。

- **当前无害**：`rag_rerank` 是启动时读取的配置，改它必须重启进程，重启即清空进程内缓存；
- **未来有坑**：若后续做**运行时热切换**策略，或同一进程里 admin 试跑某策略与线上默认策略并发，
  两者会**命中同一缓存 key**、互相串结果——且这种串是"看起来随机"的，很难查。

**建议**：key 里加上策略名，成本一行、消除未来隐患：

```python
key = (question.strip().lower(), top_k, settings.rag_rerank)
```

### P3-1（低）：`top_k` 用真值判断，`top_k=0` 会返回**全部**

`RerankStrategy.rerank` / `NoopStrategy.rerank` / `LexicalStrategy.rerank` 均写作
`out[:top_k] if top_k else out`：当 `top_k=0` 时返回**全部**而非空。

- **当前不触发**：`retrieve()` 里 `top_k = top_k or settings.rag_top_k`，0 会被兜成默认值，传到重排层时恒 ≥1；
- 但语义上 `top_k=0` 应为空。建议改 `if top_k is not None`，把边界收严。

### P3-2（低）：基类 `rerank` 逐个 `score()`，重策略需自行 override

基类默认实现是 `[(self.score(q, d), i, d) for ...]`——对 `Lexical` 无碍（它 override 了 `rerank` 走批量 `score_all`）。
但**未来的交叉编码器策略**（`C33` 的 `bge-reranker`）若只实现 `score()`，会退化成 **O(n) 次串行模型调用**，
性能可能不可接受。建议在基类 docstring 明确一条："计算昂贵的策略**应 override `rerank` 做批处理**"，
或提供 `score_batch()` 默认钩子。仅提示，不阻断。

### P3-3（低·方法学与流程）

1. **评测样本量 25**：`hit@1=92%` 时，**1 道题的翻转 = ±4 个百分点**。当前 −0.04 的结论方向可靠
   （与 `C20` 同数据独立印证），但幅度在噪声量级内。建议在 `eval_rerank.py` 输出里标注样本量，避免后续
   被当精确值引用。
2. **退出码语义**：`return 0 if improved else 1` —— 退出码 `1` 在此表示"**跑完了，结论是未达标**"，
   是**预期结论**而非脚本失败。当前无 CI（`.github/workflows/` 不存在），无影响；若日后有人把评测接成
   门禁，`1` 会被误判为"构建失败"。建议在脚本头部注明"`1` 是预期结论码，不可作为 CI 失败信号"。
