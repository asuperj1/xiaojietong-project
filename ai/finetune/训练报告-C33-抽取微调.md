## 0. 结论摘要（先给判断，再给证据）

| 验收线（`ai/finetune/README.md` 定义） | 要求 | 实测 | 判定 |
|---|---|---|---|
| ① 同 prompt 下超过「基座 + 优 prompt」 | ≥ 0.4767 | **0.7579**（V0-naive@k=0） | ✅ +28.12 pt |
| ② 比基座同 prompt 提升 | ≥ +15 pt | **+45.36 pt**（0.3043 → 0.7579） | ✅ |
| ③ 证明能力进权重而不是上下文 | 微调@k=0 优于「基座 + 16 条示例」 | 0.7579 > **0.7182** | ✅ |

一句话：**抽取专用微调把该任务从 0.30（基座）／0.4767（基座+优 prompt）／0.4795（C34 对话微调）
提到 0.7579，并且让「写长 prompt 补规则」这条路线失去价值 —— 换微调模型后 V3 反而比 V0 差。**

## 1. 目标

C34 实测「对话微调不提供抽取能力增益」，C35 实测「同一对话微调模型只要 prompt 写好就能到 0.4795」，
两条合起来说明：**增益在 prompt 里，不在权重里**。C33 要回答的是：把标注好的抽取数据
真正喂进梯度，能不能让能力落到权重上 —— 从而让线上不必依赖 919 字符的长 prompt。

## 4. 训练配置

```bash
python ai/finetune/train.py \
    --base_model D:/models/Qwen2.5-3B-Instruct \
    --data  ai/finetune/data/extract_train.jsonl \
    --eval_data ai/finetune/data/extract_dev.jsonl \
    --output ai/finetune/out/xjt-extract-3b \
    --epochs 3 --early_stopping_patience 3 --eval_steps 50
```

| 项 | 值 |
|---|---|
| 量化 | 4bit **NF4** + double quant，compute dtype bf16 |
| LoRA | r=16 / α=32 / dropout 0.05，target = q,k,v,o,gate,up,down |
| 可训练参数 | **29,933,568 / 3,115,872,256 = 0.9607%** |
| batch | `per_device_train_batch_size=1` × `grad_accum=8`（等效 8） |
| 优化 | lr 1e-4，cosine，warmup 20，bf16 |
| 序列 | `max_len=1024`，ChatML（`apply_chat_template`），**整序列 loss**（见 §9） |
| 评估 | 每 50 步评 dev，`load_best_model_at_end`（按 `eval_loss`），早停耐心 3 |

| 步 | 50 | 100 | 150 | 200 | 243 |
|---|---|---|---|---|---|
| dev `eval_loss` | 0.2129 | 0.0722 | 0.0570 | 0.0533 | **0.0528** |

### 6.3 关键发现：微调之后，**长 prompt 反而有害**

| 对比 | 在**基座** `qwen2.5:3b` 上（C35） | 在**本模型**上（C33） |
|---|---|---|
| `V3-optimized@k=0` − `V0-naive@k=0` | **+17.24 pt**（95% 区间 [+5.36, +28.78]，显著为正） | **−3.45 pt**（[−16.04, +8.79]，不显著） |
| `V3-optimized@k=1` − `V0-naive@k=1` | −0.58（不显著） | **−7.38 pt**（[−14.83, −1.52]，显著为负） |
| `V3-optimized@k=2` − `V0-naive@k=2` | −6.35（不显著） | **−7.96 pt**（[−15.68, −1.07]，显著为负） |
| `V3-optimized@k=3` − `V0-naive@k=3` | +2.78（不显著） | **−8.39 pt**（[−16.62, −1.17]，显著为负） |

解释（也是本项目第一次拿到这条证据）：
V3 里补的三条规则（日期基准、`deadline` 何时为 `null`、`entities` 口径）在基座上是**必要补丁**，
但微调已经把同样的规则写进了权重 —— 再在 prompt 里重复一遍，等于把输入推到训练时没见过的
分布上（训练集的 system 就是 V0-naive 那 220 字符），于是掉点。
**⇒ 部署结论：`xjt-extract-3b` 应配 V0-naive 简洁 prompt（147 token，比 V3 省 429 token/次）。**

（这也是 `extract_bench.py` 的 `prompt_mismatch` 自检想拦的事：训练 prompt 与评测 prompt
不一致时，提升不可归因；本次是有意为之，且两档都测了，故结论成立。）

# 4) 合并 → GGUF → 注册（Ollama 0.33 的纯 safetensors 导入在 Windows 上不可用，见 §8 第 2 条）
python ai/finetune/merge_lora.py --base_model D:/models/Qwen2.5-3B-Instruct \
    --adapter ai/finetune/out/xjt-extract-3b --output D:/models/xjt-extract-3b-merged

## 8. 过程中修掉的 3 个真实坑（都不是「环境问题」，是代码问题）

这三条都在本次提交里改掉了，并且都有回归测试：

1. **`train.py` 加评估后必崩（batch>1 无法 pad `labels`）**
   transformers 5.17 的 `DataCollatorForLanguageModeling` 只 pad `input_ids/attention_mask`，
   已 tokenize 的 `labels` 会被原样丢给 `tokenizer.pad` 转 tensor ⇒
   `ValueError: Unable to create tensor ... (labels) have excessive nesting`。
   旧脚本 `per_device_train_batch_size=1` 单样本不需要 padding，所以这个 bug **一直潜伏**；
   加上开发集评估（默认 eval batch=8）后，第一次评估就炸在第 50 步。
   ⇒ 换成显式 `PadCollator`：三个 key 一起右补齐，**补齐位的 label 用 −100**（顺带修掉
   「让模型去拟合 pad token」的隐患）；回归测试 `ai/finetune/tests/test_train_padding.py`（8 条，无需 torch）。
2. **`save_total_limit` 与 `load_best_model_at_end` 冲突**
   限制保留数会把早期的最优 checkpoint 删掉，回载时报 best checkpoint not found。
   ⇒ 开评估时不设上限（adapter 只有几十 MB）。
3. **评测脚本会把「服务没起来」静默算成「模型 0 分」**
   注册模型时踩到：Ollama 0.33 支持 `--experimental` 直接导入 safetensors 目录且**报告成功**，
   但推理时会走 MLX runner（Apple 平台）⇒ 每条请求 HTTP 500
   `mlx runner failed: MLX not available`。
   而评测脚本只在控制台 print 一行 ⚠️，**报告里只剩 `micro-F1=0.0 / 解析失败=24`**，
   16 个配置全算成 0.0 —— 那堆 0.0 和「模型真的不会」长得一模一样。
   ⇒ 两处修复：① `extract_bench.py` 记录并在报告里显示 `transport_errors`，
   失败过半**直接中止**并回显原始错误；② `prompt_opt.py` 的「复现校验」只在
   「真 ollama 后端 + 就是发布那个数字的模型」时才判一致，否则标注**不适用**
   （否则换模型后第六节会印一条假告警，让人去查不存在的问题）。

另：下载基座时 `hf_hub_download` 被硬杀后**不复用** `.incomplete`（每次换随机后缀）且留 `.lock`，
「杀掉重试」等于每次从 0 重下 ⇒ 改用 `Range: bytes=N-` 自建续传；
校验也不能拿 HTTP `ETag`（镜像返回的是 `xetHash`），权威哈希是 tree API 的 `lfs.oid`
—— 拿错基准会把**完整文件误判为损坏**（本次踩过）。

## 9. 诚实边界（不省略）

- **训练集是合成的、评测集是人工编写的**（同域不同源）⇒ 泛化性**未验证**：
  真实 `campus_notice` 只有 10 行，只能做定性抽查。0.7579 只代表「在这套评测集上」。
- **评测集只有 24 条**：几个百分点的差异可能就是抽样噪声（所以脚本给配对自助法 95% 区间，
  区间跨 0 一律按「不显著」处理）。0.7579 与 0.4767 差 28 pt，远超噪声量级，结论稳。
- **整序列 loss（未做 assistant-only mask）**：模型也在学「生成 system 段」，抽取任务更优的做法
  是只对 assistant 段算 loss。本次保留原样是为了与 C34 的 `xjt-3b` **同配方可比**；
  下一轮迭代应作为首要对照项（配合 §6.3，prompt 段占比不小）。
- **`importance` 的标注边界本身模糊**（评测集里同为「提交材料截止」，E02 记 4、E17 记 5），
  与 C32 的 Cohen's Kappa 同源；该字段上限受标注一致性限制，不是模型问题。
- **未与真实人工标注的训练集对比**：C31/D12 的人工标注量还没到能重训的规模，
  「合成 800 条」是有意的低资源方案，这一条的结论不能外推到「真实数据也这样」。
- 单条延迟 0.914 s 是 **f16 GGUF、未量化**下的数字；线上若改用 q4 量化需要重新评测
  （本次没有测量化档，不做无依据的外推）。
